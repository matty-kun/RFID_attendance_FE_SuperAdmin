# RFID Attendance System
## API Contract
**Corrected vFinal • Frontend ↔ Backend Agreement**

This contract is aligned with the finalized PostgreSQL schema and the settled Product decision that attendance opens/closes automatically by schedule. It excludes unsupported or unresolved v1 behaviors rather than inventing them.

---

## 1. Scope and Conventions

* **Base path:** `/api/v1`
* **Format:** JSON
* **Authentication:** `Authorization: Bearer <Supabase JWT>`
* **System roles:** `super_admin`, `admin`, `student`. Only `super_admin` and `admin` can access management and RFID attendance-operation endpoints. Student access is limited to student-facing features when those endpoints are enabled.
* **IDs are opaque UUIDs.** Clients must not infer meaning from an ID value.
* **Timestamps use ISO 8601** with timezone offset.
* **Official attendance timestamps** are generated by the backend/database, not supplied by the client.
* **Attendance is schedule-controlled automatically;** there are no manual open/close/reopen endpoints in v1.
* **Success envelope:** `{"success": true, "data": ...}`
* **Error envelope:** `{"success": false, "error": {"code": "...", "message": "..."}}`
* **Error codes are stable machine-readable strings.** Human-readable messages may change without breaking the client.

---

## 2. Core Product Rules Reflected by the API

* A student is resolved from `rfid_uid`; the scan client must not choose `student_id`.
* A student may have at most one `time_in` and one `time_out` per Attendance Session.
* A session may allow multiple locations for `time_in` and a different set for `time_out`.
* For `time_in`, current server/database time must fall within `time_in_start` through `time_in_end`.
* For `time_out`, current server/database time must fall within `time_out_start` through `time_out_end`.
* Attendance outside the configured schedule is rejected with `outside_time_window`.
* When creating or updating a session, `session.date` must fall inside its parent Event date range.
* Within one Event, `(event_id, date, name)` identifies a unique Attendance Session.
* The database remains the final safety net for duplicate attendance and invalid session-location-type mappings.

### 5.2 Create Event

`POST /api/v1/events`

Creates a new Event. `created_by` is derived from the authenticated admin record.

| Property | Value |
| :--- | :--- |
| **Authentication / Role** | Authorized Super Admin / Admin |

### 5.4 Create Attendance Session

`POST /api/v1/events/{eventId}/sessions`

Creates one attendance period such as Day 1 Morning.

| Property | Value |
| :--- | :--- |
| **Authentication / Role** | Authorized Super Admin / Admin |
| **Content-Type** | application/json |

#### Request
```json
{
  "date": "2026-10-10",
  "name": "Day 1 Morning",
  "time_in_start": "07:00:00",
  "time_in_end": "07:15:00",
  "time_out_start": "11:50:00",
  "time_out_end": "12:00:00"
}
```

#### Validation
* Verify the parent Event exists.
* Validate `event.start_date <= session.date <= event.end_date`.
* Require `time_in_start < time_in_end`.
* Require `time_out_start < time_out_end`.
* Require `time_in_end <= time_out_start`, matching the finalized schema.
* Reject a duplicate `(event_id, date, name)`.

#### Success response
```json
{
  "success": true,
  "data": {
    "id": "ses_001",
    "event_id": "evt_001",
    "date": "2026-10-10",
    "name": "Day 1 Morning",
    "time_in_start": "07:00:00",
    "time_in_end": "07:15:00",
    "time_out_start": "11:50:00",
    "time_out_end": "12:00:00"
  }
}
```

#### Possible errors
| HTTP | Code | Meaning |
| :--- | :--- | :--- |
| 400 | `invalid_session_date` | Session date is outside the parent Event date range. |
| 400 | `invalid_session_period` | Session times are missing, invalid, or out of order. |
| 409 | `duplicate_session` | A session with the same event, date, and name already exists. |
| 404 | `event_not_found` | Parent Event does not exist. |
| 403 | `forbidden` | Caller cannot create sessions. |

#### Database impact
* Inserts into `ATTENDANCE_SESSIONS`.
* Database also enforces `UNIQUE(event_id, date, name)`.

### 5.8 Scan RFID / Record Attendance

`POST /api/v1/attendance/scan`

Core endpoint. Resolves the RFID, validates schedule, session, type, and location, prevents duplicates, and records attendance.

| Property | Value |
| :--- | :--- |
| **Authentication / Role** | Authorized Super Admin / Admin |
| **Content-Type** | application/json |

#### Request
```json
{
  "rfid_uid": "04A37B91",
  "session_id": "ses_001",
  "location_id": "loc_002",
  "type": "time_in"
}
```

#### Validation
* Authenticate caller and resolve `recorded_by` from the authenticated admin record.
* Validate request shape and require `type` to be `time_in` or `time_out`.
* Resolve `rfid_uid` to exactly one registered student.
* Load the Attendance Session.
* Use server/database time as the authoritative current time.
* For `time_in`, require `time_in_start <= current time <= time_in_end`.
* For `time_out`, require `time_out_start <= current time <= time_out_end`.
* Validate exact `(session_id, location_id, type)` mapping in `SESSION_LOCATIONS`.
* Check whether `(student_id, session_id, type)` already exists before insert.
* Attempt insert; if the DB unique constraint still fires because of a race condition, return `duplicate_attendance`.

#### Success response
```json
{
  "success": true,
  "data": {
    "student": {
      "id": "stu_001",
      "student_id": "2026-00123",
      "name": "Juan Dela Cruz"
    },
    "attendance": {
      "id": "att_001",
      "session_id": "ses_001",
      "location_id": "loc_002",
      "type": "time_in",
      "recorded_by": "adm_001",
      "recorded_at": "2026-10-10T07:06:21+08:00"
    }
  }
}
```

#### Possible errors
| HTTP | Code | Meaning |
| :--- | :--- | :--- |
| 400 | `unknown_rfid` | RFID UID is not assigned to a student. |
| 400 | `invalid_attendance_type` | `type` is not `time_in` or `time_out`. |
| 400 | `outside_time_window` | The selected attendance type is not currently open by schedule. |
| 400 | `invalid_location` | Location is not allowed for this session/type. |
| 409 | `duplicate_attendance` | Student already has this attendance type for the session. |
| 404 | `session_not_found` | Attendance Session does not exist. |
| 401 | `unauthorized` | No valid authentication token. |
| 403 | `forbidden` | Caller cannot record attendance. |

#### Database impact
* Reads `STUDENTS`, `ATTENDANCE_SESSIONS`, `SESSION_LOCATIONS`.
* Inserts into `ATTENDANCE_RECORDS`.
* Database enforces `FK(session_id, location_id, type) -> SESSION_LOCATIONS` and `UNIQUE(student_id, session_id, type)`.

#### Notes
* Client must not send `student_id`, `recorded_by`, or official `recorded_at` for the RFID scan flow.

## 6. Core RFID Scan Validation Order

```
POST /api/v1/attendance/scan
  |
  v
 1. Authenticate caller
 2. Validate request shape
 3. Resolve rfid_uid -> student
 4. Load Attendance Session
 5. Validate type (time_in / time_out)
 6. Read authoritative server/database time
 7. Validate current time against the configured session period
 8. Validate session_id + location_id + type in SESSION_LOCATIONS
 9. Check duplicate student_id + session_id + type
10. Insert ATTENDANCE_RECORDS row
11. Return stable success/error response
```

---

## 7. Validation and Error Reference

| Validation | Backend check | HTTP | Error code |
| :--- | :--- | :--- | :--- |
| **RFID registered** | Resolve `rfid_uid` to student | 400 | `unknown_rfid` |
| **Attendance type valid** | `type` in `{time_in, time_out}` | 400 | `invalid_attendance_type` |
| **Schedule window open** | Current server time within configured period | 400 | `outside_time_window` |
| **Location allowed** | Exact `SESSION_LOCATIONS` mapping exists | 400 | `invalid_location` |
| **No duplicate attendance** | No same `student_id` + `session_id` + `type` | 409 | `duplicate_attendance` |
| **Session date valid** | `Event start_date <= session.date <= end_date` | 400 | `invalid_session_date` |
| **Unique session identity** | No duplicate `event_id` + `date` + `name` | 409 | `duplicate_session` |
| **Authorization** | Authenticated role permitted | 403 | `forbidden` |

---

## 8. HTTP Status Guidance

* **200** - Successful `GET`, `PATCH`, `PUT`, or successful scan where appropriate.
* **201** - Resource created successfully (`POST` create endpoints).
* **400** - Invalid input or domain validation failure.
* **401** - Missing or invalid authentication.
* **403** - Authenticated caller is not authorized.
* **404** - Requested resource does not exist.
* **409** - Conflict, especially uniqueness/duplicate conflicts.

## 9. Deferred / Excluded from Current Phase

* **Student feedback submission endpoint:** Deliberately removed/deferred for now per Product Lead decision.
* **Manual session open/close/reopen:** Not included because attendance is automatically controlled by the configured schedule.
* **Attendance correction endpoint:** Deferred until Product and Engineering agree how corrections are audited. The current schema has no audit/history table, so destructive edits would weaken traceability.
* **Location creation/deletion endpoints:** Deferred until physical kiosk deployment protocol is finalized.
* **Bulk student CSV imports:** Deferred to future admin batch tools.

## 10. Change Management

This is a shared FE/BE contract. Any change to endpoint paths, HTTP methods, request fields, response shapes, authorization, or stable error codes must be updated here before or in the same change that modifies implementation. Breaking changes must be coordinated with Frontend before merge.

## 11. Definition of Ready for FE Integration

* Endpoint path and HTTP method are agreed.

* Backend validation and error codes are defined.
* Success response shape is stable.
* Authentication/authorization requirements are explicit.
* Endpoint is testable in Postman/Bruno.
